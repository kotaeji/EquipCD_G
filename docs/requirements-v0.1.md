## 1. 문서 사용법과 간단한 기능개발요구 템플릿

### 1.1 상태 표기

- [확정]: 사용자 요구 또는 확인된 F1~F8 제품 요구. 구현할 때 지켜야 하는 제품 방향이며, 일정·전체 구현 승인을 뜻하지 않는다.
- [설계 제안]: 요구를 구현 가능한 단위로 나누기 위한 권고. 승인 전에는 확정 요구로 승격하거나 코드에 고정하지 않는다.
- [미정]: 결정 또는 외부 계약 확인이 필요하다. 빈칸을 개발자의 임의 판단으로 채우지 않는다.
- [예시]: 이해와 검수 설계를 돕는 문서상의 가상 데이터·상황. 성능 목표, 실제 하드웨어 사양, 확정 스키마가 아니다.

필드·알고리즘·파일 구조·복구 정책은 [설계 제안], 외부 계약 불명은 [미정]이다.

### 1.2 기본 템플릿: 8항목

1. **ID / 목적·사용자**: 누가 어떤 문제를 해결하는지, 연결된 요구 ID.
2. **상태 / 범위**: 확정 요구, 제외, 제안, 미정과 이번 구현 포함 여부.
3. **입력 / 출력**: 필요한 데이터, 생성·변경되는 객체, 보존해야 할 정보.
4. **정상 흐름**: 사용자의 시작 행동부터 결과 확인까지.
5. **세부 규칙**: 단위 작업, 데이터 관계, 판단·승인·표시 규칙.
6. **예외 / 오류 처리**: 실패, 불완전 입력, 취소, 복구, 안전 경계.
7. **완료 검증**: Given / When / Then 형식의 정상·오류·보존·사람 승인 검수.
8. **의존 / 미정**: 선행 기능, 계약, 질문, 구현 전 결정할 사항.


## 2. 제품 목적·사용 환경·범위와 용어

### 2.1 제품 정의

[확정] 장비 소프트웨어 플랫폼 개발팀이 실제 장비가 없는 초기 단계에서 장비 컨셉을 구성하고 시험하는 도구다. 유닛과 디바이스를 드래그앤드롭으로 배치·연결하고, 개략 시퀀스와 시간·조건 기반 논리 시뮬레이션으로 설계의 빈틈을 찾는다. 완성 장비를 직접 제어하는 애플리케이션이 아니다.

[확정] React + TypeScript 웹 UI와 C# WPF UI를 별도로 제공한다. 화면을 같은 코드로 공유한다는 요구가 아니라 공통 파일 형식·동작 규칙·데이터 의미가 같아야 한다는 요구다. 집에서는 MacBook, 회사에서는 Windows를 사용한다. 봇은 회사 PC에 직접 접근하지 않는다. 사용자가 GitHub에서 받아 WPF를 빌드·실행·검증한다. 저장소와 경로는 아직 미정이고 기존 IssueReporter 프로젝트와 혼동하거나 섞지 않는다. WPF의 .NET 버전도 구현 전 결정한다.

[확정] 1인 로컬 사용을 먼저 지원한다. 이후 협업에 대비해 고유 ID, 형식 버전, 설계 데이터와 사용자 뷰 설정의 분리를 초기부터 고려한다. 서버 권한, 충돌 해결, 실시간 동시 편집은 후속 범위다. 지금 사용자 계정·서버·협업 데이터베이스가 필요하다고 가정하지 않는다.

### 2.2 작업 단위

- [확정] Workspace: 여러 Project와 공통 Asset Library를 묶는 작업 공간. 생성·열기·최근 작업 진입점이 있다.
- [확정] Project: 하나의 장비 배치·연결·시퀀스·시뮬레이션 설정을 담는 작업 단위. 여러 프로젝트를 탭으로 열 수 있다.
- [확정] Equipment: 설계 대상으로서의 장비 최상위 개념. Unit과 Device로 분해한다.
- [확정] Unit/Module: 큰 장비 설계 작업 단위. Device를 포함하고 외부에서 사용할 Action과 능력을 정의한다.
- [확정] Mechanism Model: Equipment·Unit·Device·Signal·Position·Action·Process·Material·Constraint가 연결된 단일 설계 원본이다.
- [설계 제안] 화면·외부 자료는 모델 ID를 참조하며 복제·역매핑의 동일성 규칙을 명시한다.

### 2.3 범위 경계

[확정] 기계 CAD의 치수·강도 설계, 전기도면 작성, 정밀 물리·충돌 검증은 이 도구의 책임이 아니다. 정밀 물리는 VC 등에 위임한다. 실제 장비 제어는 Core 런타임, 현장 운영은 AuroraOP의 영역이다. 향후 OP의 운영 데이터·자재 실패 사례를 다음 설계로 되먹임하는 방향은 있지만 현재 상세 연동 계약이나 시제품 범위는 없다.

[확정] 첫 시제품 기준은 로컬 워크스페이스·프로젝트 저장/열기, 라이브러리 배치/연결/속성, 개략 시퀀스, 실행/일시정지/초기화/상태, 시간·조건 기반 논리 시뮬레이션이다. 실제 장비 연결과 정밀 물리 충돌은 제외한다. F1~F8 추가 이후 최종 우선순위를 다시 정해야 하므로 이 기준을 F1~F8 전체 구현 확정으로 해석하지 않는다.

[설계 제안] 가상 시간, 결정적 실행, 일시정지 중 시간 동결, 초기화 시 초기 조건 복원, 타임아웃 오류 전이, 물류 연결과 논리 연결의 분리는 첫 시제품의 동작 규칙 후보다. 이후 절은 이를 상세화하되 사용자 확정 사실로 취급하지 않는다.

### 3.2 관계와 불변식

[확정] 구조는 Equipment > Unit > Device이고, Unit은 Action을 통해 제공 능력을 드러낸다. Process는 필요한 Action과 자재 상태 전이를 요구한다. F6은 이 요구와 제공을 비교하며 F7은 같은 모델을 기준으로 변형 후보를 만든다. F8은 별도 모델을 새로 만드는 기능이 아니라 동일 모델을 외부 계약에 맞춰 매핑하고 실측 정보를 다시 연결하는 기능이다.

[설계 제안] Device 소유 Unit은 하나로 두고 다른 Unit 능력은 Action으로 참조한다. 이름은 표시와 후보 매칭에 쓰고 ID는 동일성에 쓴다. 동명이인 객체를 이름만으로 병합하지 않는다. 삭제 전 참조를 조회하여 해제·대체·취소를 선택한다. 복제 시 새 객체 ID를 부여하고 원본 계보는 별도 기록한다. 외부 객체 ID와 앱 내부 ID는 구분한다.

[미정] 중첩 Unit의 허용 깊이, 프로젝트 간 참조 방식, 하나의 프로젝트에 Equipment 여러 개를 둘 수 있는지, 자재 정의의 라이브러리 공유 범위, 외부 참조의 상대경로 기준은 결정되지 않았다.

### 3.3 출처·가정·확인·버전·null

- [확정] 추출 후보에는 출처와 신뢰도 및 사람 확인 상태가 필요하다. 가정과 미정은 Gap 및 Export까지 유지한다.
- [설계 제안] source는 파일 식별·파일 리비전·페이지 또는 시트/셀·도면 대상·USD prim path·추출 방식·근거 설명을 담는다. 해당 형식에 없는 위치 표현은 억지로 채우지 않는다. 원본 파일 전체를 모델에 복제하는지는 별도 정책이다.
- [설계 제안] assumption은 값의 사실 여부와 독립된 메타정보다. 가정 이유·제안자·관련 요구·실측 대체 필요 여부를 기록한다. 예를 들어 수치가 들어 있어도 가정이면 확정 사양으로 표시하지 않는다.
- [설계 제안] confirmation은 미확인/사람확인/거절/재확인필요 상태를 후보로 둔다. 확인자는 로컬 사용자 표시로도 시작 가능하나 법적 안전 승인 체계로 오해하지 않도록 한다. 근거가 바뀌면 이전 확인의 유효성을 재검토한다.
- [설계 제안] 형식 버전, 모델 변경 리비전, 에셋 정의 버전, 외부 도구 버전을 서로 다른 항목으로 관리한다. 하나의 숫자를 모든 버전에 재사용하지 않는다.
- [설계 제안] null은 알려지지 않았거나 미입력인 값이지 0·false·빈 문자열이 아니다. 해당 없음과 미정은 상태로 구별한다. 필수 값이 null이면 저장 가능 여부와 실행 가능 여부를 분리하고 실행 차단 사유를 표시한다.
- [미정] 버전 문자열 규칙, 확인 이력의 필수 보존 기간, 로컬 사용자 식별, 첨부 원본 패키징은 아직 결정하지 않았다.

## 4. 공통 기능 C01~C09

공통 AC도 모두 미실행이다. 아래 8항목에서 [설계 제안] 규칙은 승인 후 검수에 적용한다.

### C01. 워크스페이스·프로젝트

1. **ID/목적**: C01-01 생성·열기·최근 작업, C01-02 다중 탭, C01-03 저장·재열기.
2. **상태/범위**: [확정] 여러 Project와 공통 라이브러리. [미정] 웹 저장·자동저장·DB.
3. **입출력**: 이름/선택 파일 → Workspace와 Project. 최근 경로는 뷰 설정과 분리 [설계 제안].
4. **흐름**: 시작 → 생성/열기 → 탭 편집 → 저장 → 재열기.
5. **규칙**: [설계 제안] 탭 전환은 변경을 버리지 않고 동일 파일 중복 열기는 기존 탭으로 안내한다.
6. **예외**: [설계 제안] 저장 실패는 메모리 변경을 유지하고 재시도, 최근 경로 누락은 재지정한다.
7. **검증**: C01-AC1 Given 두 Project When 각 저장·재열기 Then 데이터가 섞이지 않는다. C01-AC2 Given 저장 실패 When 닫기 취소 Then 변경 유지. C01-AC3 Given 최근 경로 누락 When 열기 Then 원본 덮어쓰기 없이 안내.
8. **의존/미정**: C05/C06, Workspace 전체/Project 단위 저장 경계.

### C02. AML 라이브러리

1. **ID/목적**: C02-01 AML, C02-02 초기 8종, C02-03 정의·인스턴스·시각 분리.
2. **상태/범위**: [확정] AutomationML 기본. JSON은 앱 메타데이터 후보이지 AML 대체가 아니다. 표준에 없는 시퀀스·시뮬·뷰는 앱 확장/별도 데이터이며 AML 표준 자체로 주장하지 않는다.
3. **입출력**: [확정] 실린더·푸셔·바코드리더·컨베이어·스토퍼·갠트리·피커·센서 AML 샘플. 속성 타입/단위, 포트 방향/의미, 명령·상태·완료 조건 정의.
4. **흐름**: 정의 선택 → 인스턴스 배치 → 속성/신호/Action 연결.
5. **규칙**: [설계 제안] 정의 버전 고정·자동 업데이트 금지·명시적 변경 비교. 사용자 확정과 구별한다.
6. **예외**: [설계 제안] 파싱·참조·필수 의미 누락을 진단하고 단위를 임의 보충하지 않는다.
7. **검증**: C02-AC1 Given 두 인스턴스 When 하나 수정 Then 다른 인스턴스 불변. C02-AC2 Given 완료 조건 누락 When 검사 Then 미정 표시. C02-AC3 Given 지원 버전 불명 When 가져오기 Then 적합성 완료 주장 금지.
8. **의존/미정**: AML/CAEX 버전·공식 XSD·AML 매핑·이미지 참조/패키지 검증 미정. 참고: [AutomationML 소개](https://www.automationml.org/about-automationml/automationml/) 및 [공식 Specifications](https://www.automationml.org/about-automationml/specifications/). 특정 스키마 검증 근거가 아니다.

### C03. 시각·테마

1. **ID/목적**: C03-01 도식/사진, C03-02 테마 3종, C03-03 공통 행동.
2. **상태/범위**: [확정] 알아보기 쉬운 도식 기본, 가능하면 실제 사진 토글, 없으면 도식 대체.
3. **입출력**: [확정] A 밝은 엔지니어링(흰색·회색·파랑), B 어두운 관제(딥네이비·청록), C 따뜻하고 차분함(회백색·청록)을 선택한다. 고정 테마가 아니다.
4. **흐름**: 선택 → 리소스 확인 → 표시 → 같은 모델 작업 지속.
5. **규칙**: [확정] 레이아웃/행동 및 배치·연결·논리 상태 보존. 실제 사진/생성 실사풍 구별, 출처·라이선스 관리. [설계 제안] 앵커 정규화·테마 user-local 저장.
6. **예외**: [설계 제안] 누락 이미지는 도식 대체, 라이선스 불명은 자동 재배포 보류.
7. **검증**: C03-AC1 Given 연결 모델 When 토글 Then 의미 불변. C03-AC2 Given 사진 없음 When 사진 선택 Then 도식 대체. C03-AC3 Given 생성 이미지 When 상세 보기 Then 실제 촬영과 구별·출처 표시.
8. **의존/미정**: 패키징·뷰 호환. 목업은 실행 증거가 아니다.

### C04. 논리 시뮬레이터

1. **ID/목적**: C04-01 실행/일시정지/초기화/상태, C04-02 시간·조건 논리 실행.
2. **상태/범위**: [확정] 실제 장비 연결·정밀 충돌 제외. 이하 실행 정책은 [설계 제안].
3. **입출력**: 모델/시퀀스/설정 → 단계·신호·자재 상태·시간·오류. 설계/런타임 분리.
4. **흐름**: 검사 → 초기화 → 실행 → 정지/재개 → 완료/오류.
5. **규칙**: 가상 시간·결정적 실행·일시정지 시간 동결·초기 조건 복원·타임아웃 오류 전이·물류/논리 연결 분리.
6. **예외**: 미정 필수 조건·무진행·동시 쓰기 충돌을 임의 진행하지 않고 원인 단계 표시.
7. **검증**: C04-AC1 Given 지연 중 When 정지/재개 Then 정지 기간 제외. C04-AC2 Given 진행 중 When 초기화 Then 시작 상태 복원. C04-AC3 Given 완료 신호 없음 When 타임아웃 Then 오류 전이 기록.
8. **의존/미정**: 시간 해상도·동시 이벤트·분기/병렬·경계 비교·실행 중 편집은 13절 합의 필요.

### C05. 공통 파일·호환

1. **ID/목적**: C05-01 동일 의미, C05-02 버전, C05-03 무결성.
2. **상태/범위**: [확정] 웹/WPF 공통 파일·규칙. [미정] 컨테이너·직렬화·저장 기술.
3. **입출력**: 설계·출처·가정·미정 읽기/쓰기.
4. **흐름**: 버전/참조 검사 → 편집 → 저장 → 다른 플랫폼 확인.
5. **규칙**: [설계 제안] 앱/형식 버전 분리, 변환 시 원본 보존.
6. **예외**: [설계 제안] 미지원 버전은 거부/읽기 전용, 파손 파일을 빈 모델로 덮어쓰지 않음.
7. **검증**: C05-AC1 Given 웹 파일 When WPF 열기 Then 의미 보존. C05-AC2 Given 미지원 버전 When 열기 Then 원본 불변. C05-AC3 Given 누락 참조 When 검사 Then 원인 ID 표시.
8. **의존/미정**: AML 공식 검증·D01~D04, 플랫폼 전용 뷰 보존 정책.

### C06. Undo·취소·격리

1. **ID/목적**: C06-01 Undo/Redo, C06-02 변경 취소.
2. **상태/범위**: [확정] F2 Undo/Redo. 나머지 트랜잭션 정책은 [설계 제안].
3. **입출력**: 편집 → 모델 리비전·변경 요약.
4. **흐름**: 검사 → 적용 → Undo → Redo.
5. **규칙**: 다중 편집은 일관 복원. 실행 중 모델 편집 차단 우선 검토, 뷰 이동은 허용.
6. **예외**: 외부 파일·서버 요청은 Undo로 회수되지 않을 수 있음. 초기화와 Undo 구별, 취소 시 반쪽 객체 금지.
7. **검증**: C06-AC1 Given 연결 모델 When Undo/Redo Then 연결 보존. C06-AC2 Given 실행 중 When 편집 Then 승인된 격리 정책 표시. C06-AC3 Given 가져오기 When 취소 Then 모델 불변.
8. **의존/미정**: 이력 저장·상한·삭제·실행 중 편집 정책.

### C07. AI·평가기 어댑터

1. **ID/목적**: C07-01 교체성, C07-02 VC/Omniverse 입력·평가.
2. **상태/범위**: [확정] 불필요 AI 금지·서비스/평가기 교체 가능. [미정] 공급자·전송 동의·보안.
3. **입출력**: 지정 데이터 → 후보/근거/실패.
4. **흐름**: 요청 → 동의 확인 → 응답 검사 → 사람 선택.
5. **규칙**: [설계 제안] 최소 전송, 외부 응답은 검증할 자료이지 실행 명령이 아님.
6. **예외**: [설계 제안] 미동의/오프라인/잘못된 응답에서 원본 유지, 직접 편집 경로 보존.
7. **검증**: C07-AC1 Given 미동의 When 요청 Then 미전송. C07-AC2 Given 불완전 응답 When 검사 Then 원본 불변. C07-AC3 Given 구조 직접 지정 When 변환 Then AI 미호출.
8. **의존/미정**: 비용·상한·취소·로그·VC 버전/설치 계약.

### C08. 진단·사람 확인

1. **ID/목적**: C08-01 미정/가정, C08-02 근거 이동, C08-03 자동 안전 확정 금지.
2. **상태/범위**: [확정] 후보·경고·Gap 근거·Export 가정 유지.
3. **입출력**: 객체/출처/리비전 → 진단·관련 화면.
4. **흐름**: 근거 확인 → 수정/사람 확인 → 재검사.
5. **규칙**: [설계 제안] 오류 심각도와 확인 상태 분리, 숨김과 해결 구별, 오래된 분석 표시.
6. **예외**: [확정] 안전/간섭 자동 확정 종료 금지. [설계 제안] 출처 누락을 알리고 확인 이력 유지.
7. **검증**: C08-AC1 Given 가정 When Export Then 표기 유지. C08-AC2 Given 안전 후보 When 재분석 Then 자동 승인 금지. C08-AC3 Given 출처 누락 When 상세 Then 누락 안내·모델 이동.
8. **의존/미정**: 로컬 확인의 기록 필드. 팀 권한은 후속.

### C09. 환경·접근 경계

1. **ID/목적**: C09-01 문서 단계, C09-02 회사 PC, C09-03 저장소 분리.
2. **상태/범위**: [확정] 지금 코딩 금지·문서만. 구현·테스트 미수행.
3. **입출력**: 문서/결정 → 승인된 후속 계획.
4. **흐름**: 범위 승인 → 환경 확인 → 추후 구현 → 사용자 Windows 검증.
5. **규칙**: [확정] 회사 PC 직접 접근 금지, 사용자가 GitHub에서 받아 WPF 빌드·실행.
6. **예외**: [설계 제안] Windows 결과 없으면 미검증, 웹 통과로 대체 금지.
7. **검증**: C09-AC1 Given 인수 When 착수 기록 Then IssueReporter 분리 명시. C09-AC2 Given Windows 결과 없음 When 보고 Then 성공 주장 금지. C09-AC3 Given 현재 단계 When 산출물 확인 Then 문서뿐.

## 5. F1 Input Hub — 입력과 후보 확인

### 1) ID / 목적

[확정] F1-01 직접 설계, F1-02 설계 자료 추출, F1-03 VC/3D 입력, F1-04 공통 후보표와 사람 확인. 실제 장비가 없는 설계자가 출발 자료에 관계없이 동일 Mechanism Model을 구성한다. 자료가 없어도 시작할 수 있어야 한다.

### 2) 상태 / 범위

[확정] 경로 A는 직접 입력·빈 캔버스·유사 장비 템플릿 복제·유닛 라이브러리를 우선 지원한다. 경로 B는 Schematic·BOM·유닛 리스트가 들어 있는 PDF/DWG/표 파일(XLSX 포함)에서 유닛·축·I/O 후보와 출처 페이지 등을 추출한다. 경로 C는 VC/3D USD의 prim path별 후보, 탑뷰, 경계, part 분리 수준을 점검한다. [미정] 각 형식의 지원 버전·파서·추출 정확도·스캔 문서 OCR 지원. 특정 확장자 전체를 완벽히 읽는다고 약속하지 않는다.

### 3) 입력 / 출력

입력은 문서/도면/표/3D·직접 입력이다. 출력 후보표는 디바이스·출처·신뢰도·사람 확인을 담고, 확인 대상을 모델에 반영한다. [설계 제안] 후보표 열은 후보 ID, 예상 종류, 이름, 소속 Unit, 관련 축/I/O, 원문 위치, 신뢰 근거, 미정 속성, 확인 상태, 반영 대상 ID로 구성한다. PDF 페이지와 XLSX 시트/셀, USD prim path를 같은 문자열로 뭉개지 말고 위치 유형을 구별한다.

### 4) 정상 흐름

경로 선택 → 원본 열기/직접 입력 → 구조와 지원 수준 검사 → 후보표 작성 → 원문과 후보 비교 → 사람이 배정·병합·거절·확인 → 반영 미리보기 → Mechanism Model 적용 → Canvas에서 결과 확인.

### 5) 세부 규칙

- F1-05 [확정] 신뢰도는 이름 일치, 위치, 연결 근거를 드러내야 한다. 낮은 신뢰도 항목은 사람 배정 전에 모델에 반영하지 않는다. 단순 점수만으로 확정 장치가 되지 않는다.
- F1-06 [확정] USD 입력은 prim path와 후보의 연결, 탑뷰/경계, part 분리 수준을 확인한다. 단일 덩어리 모델을 개별 디바이스로 완벽 추론했다고 처리하지 않는다.
- F1-07 [설계 제안] 중복 후보는 자동 병합 대신 동일 가능성을 표시한다. 기존 객체와의 연결도 ID·역할·근거를 보여 주고 선택하게 한다. 원문이 수정되면 기존 확인을 재확인 대상으로 바꿀 수 있다.
- F1-08 [설계 제안] 파싱, 후보 작성, 사람 확인, 반영을 별도 구현 단위로 나눈다. 지원하지 않는 페이지/요소가 있어도 성공한 후보와 실패 목록을 구별하며 원본을 수정하지 않는다.

### 6) 예외

[설계 제안] 암호화/손상/지원 불가 문서, 비어 있는 시트, 단위 불명, 모호한 이름, 너무 적게 분리된 3D를 구분한다. 추출 실패 시 빈 후보를 성공으로 표시하지 말고 직접 입력으로 이어갈 수 있게 한다. 가져오기 취소는 기존 모델을 유지한다. 외부 자료나 템플릿의 사용 권한이 불명하면 저장·배포 포함 정책을 먼저 확인한다.

### 7) 완료 검증

- F1-AC1 Given 원본 없는 신규 프로젝트 When 라이브러리에서 직접 후보를 지정·확인 Then 문서 업로드 없이 Canvas에 같은 모델 객체가 생성된다.
- F1-AC2 Given PDF/XLSX에서 추출한 후보 When 근거 선택 Then 해당 페이지 또는 시트/셀과 추출 근거를 볼 수 있고 후보 ID가 유지된다.
- F1-AC3 Given 신뢰도가 낮고 소속 미배정인 후보 When 일괄 반영 요청 Then 그 항목은 반영되지 않으며 사람 배정 필요 사유를 보여 준다.
- F1-AC4 Given USD part 분리가 불충분 When 점검 Then prim path·경계·분리 한계를 표시하고 개별 Device 확정을 자동 수행하지 않는다.
- F1-AC5 Given 기존 설계와 중복 가능한 후보 When 반영 취소 Then 기존 객체·ID·연결은 변하지 않는다. 이는 취소 정책 제안에 대한 검수다.

### 8) 의존 / 미정

C02 라이브러리, C08 확인 체계, F2 반영, 공통 출처 구조가 선행한다. 파서 선택·형식별 지원 범위·신뢰도 산식/임계값·원문 보관 정책·클라우드 추출 여부는 미정이다. 첫 시제품에 모든 입력 어댑터를 넣을지는 범위 재확정 대상이다.

## 6. F2 Mechanism Canvas — 구조·배치·연결

### 1) ID / 목적

[확정] F2-01 Equipment > Unit > Device 계층, F2-02 DnD 배치·연결, F2-03 선택·이동·정렬·Undo/Redo, F2-04 레이어·속성·Configurator 이동. 장비 구조 편집 화면이다.

### 2) 상태 / 범위

[확정] 도면이나 VC 탑뷰는 선택적 배경이며 없어도 동작한다. 레이어는 Background / Units / Axis / I/O / Positions / Flow를 제공한다. Unit 안에 Device를 넣으면 Action 편집과 연결된다. CAD 정밀 도면 편집이나 실제 장비 제어 화면은 아니다.

### 3) 입력 / 출력

라이브러리·후보표·기존 모델을 입력받아 계층, 배치, 연결, 속성 변경을 만든다. 선택 속성에는 축·신호·포지션·자재 상태·Action·Interlock 후보·미정 경고를 보여 준다. [설계 제안] Configurator 이동은 같은 객체 ID를 참조한다. 배경 이미지는 의미 객체를 대신하지 않고 출처 있는 VisualResource로 연결한다.

### 4) 정상 흐름

Unit 배치 → 내부 Device 배치 → 속성 확인 → 포트 연결 → 레이어별 구조 확인 → 정렬/이동 → Action 관련 항목 선택 → Configurator 이동 → 저장.

### 5) 세부 규칙

- F2-05 [확정] 배치·연결과 시각 표현을 함께 제공하고 도식/사진 변경에도 논리 상태를 보존한다.
- F2-06 [설계 제안] 연결은 물류 흐름, 신호/조건, 구조 소속처럼 의미 유형을 구별한다. 잘못된 포트 방향·종류를 연결하려 하면 허용 조건과 오류를 안내한다. 선이 가까이 지나가는 것만으로 연결을 만들지 않는다.
- F2-07 [설계 제안] 레이어 숨김은 객체 삭제나 시뮬 제외가 아니다. 잠금 기능을 추가할지는 미정이다. 좌표·앵커는 공통 모델 좌표와 뷰 확대율을 분리한다.
- F2-08 [설계 제안] 다중 이동/정렬을 한 Undo 단위로 취급한다. Device를 다른 Unit으로 옮길 때 Action·Signal 참조의 영향을 먼저 검사한다. 계층 이동과 캔버스 좌표 이동을 혼동하지 않는다.

### 6) 예외

[설계 제안] 순환 소속, 없는 포트, 참조가 남는 삭제, 잠긴 실행 스냅샷 편집을 구별하여 진단한다. 배경 파일 누락은 배경만 대체하고 설계 객체를 지우지 않는다. 연결 실패 중간에 반쪽 간선을 저장하지 않는다.

### 7) 완료 검증

- F2-AC1 Given 빈 캔버스 When Unit과 Device를 배치 Then Equipment > Unit > Device 관계가 만들어지고 Device에서 Action 편집으로 이동할 수 있다.
- F2-AC2 Given Background 없음 When 배치·연결·속성 편집 Then 배경 업로드를 요구하지 않고 작업을 완료한다.
- F2-AC3 Given 연결된 여러 객체 When 이동/정렬 후 Undo와 Redo Then 계층·ID·연결 대상은 보존되고 위치만 의도대로 왕복한다.
- F2-AC4 Given 숨긴 I/O 레이어와 사진 토글 When 저장 후 재열기 Then 실제 Signal·연결 의미가 사라지지 않는다.
- F2-AC5 Given 방향 불일치 포트 When 연결 시도 Then 승인된 연결 규칙에 따라 거부/경고하고 원래 연결은 보존한다. 상세 거부 규칙은 제안이다.

### 8) 의존 / 미정

C02·C03·C06, F3 속성 계약, F4 Flow 의미가 필요하다. 좌표 단위·앵커 규칙·연결 종류별 허용표·라우팅·대형 캔버스 성능 수치는 미정이다. 여기서 라우팅은 화면/연결 경로 구현을 확정하는 의미가 아니다.

## 7. F3 Unit Configurator — 능력과 Action 정의

### 1) ID / 목적

[확정] F3-01 Device 사양·신호·Position, F3-02 매개변수/pre/post 조건을 갖는 Action, F3-03 자동 제공 능력표, F3-04 정의 체크·미정·Interlock 확인. 설계자는 Unit이 무엇을 할 수 있는지를 공정에서 재사용 가능한 형태로 정의한다.

### 2) 상태 / 범위

[확정] 축·I/O·센서의 사양, 신호, 포지션을 정의한다. 능력표에는 동작·포지션·입출력·자재 상태 변화·금지 조건과 근거가 들어간다. 미정은 가정값과 함께 남겨 Gap에 제공한다. 포지션 가정값은 나중에 실측으로 역매핑한다. Interlock 후보는 사람이 확인한다.

### 3) 입력 / 출력

입력은 Unit/Device, 에셋 기본값, 사용자 사양, 추출 출처다. 출력은 Action 정의, 제공 능력표, 정의 오류/가정/미정 목록, Interlock 후보다. [설계 제안] Action의 전제와 완료는 구조화 조건을 우선 사용하고 자유 메모는 실행 조건과 분리한다. 실행 가능한 조건식 문법은 미정이다.

### 4) 정상 흐름

Unit 선택 → Device와 사양 확인 → Signal 역할·방향·값 타입 지정 → Position 지정 → Action 매개변수/pre/post 정의 → 능력표 생성 → 누락 검사 → 미정을 가정 또는 보류로 표시 → Interlock 후보 검토 → Process Composer에서 사용.

### 5) 세부 규칙

- F3-05 [확정] 제공 능력은 단순 장치 목록이 아니라 공정 요구와 비교할 수 있는 동작·조건·상태 변화 단위다. 생성된 능력의 근거를 추적할 수 있어야 한다.
- F3-06 [설계 제안] 명령 신호와 완료 신호, 현재 상태와 목표 Position을 구분한다. Action 이름만 같다고 같은 능력이라고 보지 않는다. 단위와 매개변수 허용 범위를 검사한다.
- F3-07 [설계 제안] 가정값 변경과 실제 확정값 변경을 다른 이력으로 남긴다. 실제 I/O 주소가 없어도 역할 기반 개념 Signal을 정의하되, 실제 주소가 있는 것처럼 보이지 않게 한다.
- F3-08 [설계 제안] 정의 체크를 참조 무결성, 타입/단위, 완료 조건, 자재 변화, 금지 조건으로 나눠 구현한다. 조건 누락을 임의 true로 보충하지 않는다.

### 6) 예외

[설계 제안] 없는 Signal/Position 참조, 서로 충돌하는 pre조건, 완료 조건 없는 Action, 실측 단위 불일치를 진단한다. 임시 가정으로 저장할 수 있어도 실행과 Export 준비 수준은 따로 평가한다. 사용 중 Action 삭제는 영향 공정 목록을 보여 준다. 미확인 Interlock을 기본 안전 보장으로 표시하지 않는다.

### 7) 완료 검증

- F3-AC1 Given 축과 센서를 가진 Unit When Action과 pre/post를 정의 Then 능력표에 동작·Position·I/O·자재 변화·금지 조건 및 근거가 연결된다.
- F3-AC2 Given Position 수치가 가정 When 저장·재열기 및 F8 미리보기 Then 값과 가정 상태가 함께 유지된다.
- F3-AC3 Given 없는 완료 Signal을 참조 When 정의 검사 Then 해당 Action과 누락 참조를 표시하고 정상 정의 완료로 처리하지 않는다.
- F3-AC4 Given 자동 Interlock 후보 When 사용자가 확인하지 않음 Then 후보 상태를 유지하고 자동 확정하지 않는다.
- F3-AC5 Given 실제 I/O 주소가 아직 없음 When 역할 기반 Signal로 공정 작성 Then 미정 주소를 보존하고 개념 설계 경로를 유지한다.

### 8) 의존 / 미정

C02 에셋 의미, F4 상태, F5 조건 표현, F6 비교 계약, F8 실제 주소/포지션 역매핑이 연결된다. 축 모델 종류·조건 언어·권장 단위계·한 Action의 동시 자원 사용 의미는 미정이다.

## 8. F4 Material & Flow — 자재·상태·경로

### 1) ID / 목적

[확정] F4-01 자재·캐리어 정의, F4-02 상태집합·Unit 경로, F4-03 Action/post와 상태전이 연결, F4-04 수용 능력 등 Gap 제공. 장치가 움직이는 것뿐 아니라 무엇을 어디로 어떤 상태로 옮기는지 명세한다.

### 2) 상태 / 범위

[확정] 종류, 캐리어/개별 자재, 크기, 무게, 취급 조건, 투입 간격, 상태집합, Unit 경로를 정의한다. 원래 문서의 V1은 크기·무게·상태 흐름을 다루고 재질·공차·열은 후속이었다. 이 ‘문서상 V1’ 표기를 현재 첫 시제품의 확정 우선순위로 대체하지 않는다.

### 3) 입력 / 출력

자재 정의와 Unit/Action을 입력으로 물류 경로, 상태전이 요구, 공정전이 연결, Gap 요구를 만든다. [설계 제안] Material 정의와 실행 중 개별 자재 ID, 캐리어와 적재된 자재의 관계를 분리한다. 크기/무게는 단위와 가정 표시를 동반하고 상태는 이름 및 의미를 가진다.

### 4) 정상 흐름

자재 종류 생성 → 캐리어 유무 설정 → 크기·무게·취급 조건 입력 → 초기/허용 상태 정의 → Unit 경로 연결 → 각 구간/공정의 Action과 post조건 연결 → 투입 간격 설정 → 흐름 및 수용성 검사 → Gap 확인.

### 5) 세부 규칙

- F4-05 [확정] 상태전이는 Action/post조건과 연결하여 공정전이와 Gap 요구에 사용한다. 자재 수용 능력 부족 등을 드러내야 한다.
- F4-06 [설계 제안] 위치 이동과 가공 상태 변화는 별개다. ‘가공 완료’가 다음 Unit 도착을 뜻하지 않는다. 캐리어 도착과 캐리어 안 자재 존재도 구별한다.
- F4-07 [설계 제안] Unit 수용 개수·크기·허용 무게·동시 취급 능력을 제공 능력과 대조한다. 알려지지 않은 능력은 적합이 아니라 미정으로 판정한다. 버퍼와 대기 규칙은 F7 변형의 공통 의미가 된다.
- F4-08 [설계 제안] 첫 시제품 검수는 한 자재로 좁히되 구조상 정의와 런타임 개체를 분리한다. 다중 자재의 큐·충돌·분배 규칙은 별도 승인 전 자동 확대하지 않는다.

### 6) 예외

[설계 제안] 경로의 없는 Unit, 초기 상태 미정, 허용되지 않은 상태전이, 수용 능력 미정, 단위 불일치를 따로 진단한다. 물류 선이 있다고 자동 이동시키지 않는다. 물류 수용 불가와 논리 조건 미충족을 다른 대기/오류 원인으로 표시한다. 정밀 물리 간섭을 계산한 것처럼 표현하지 않는다.

### 7) 완료 검증

- F4-AC1 Given 개별 자재와 캐리어 정의 When 경로 작성 Then 소속 관계와 Unit 경로를 볼 수 있고 상태전이가 Action/post에 연결된다.
- F4-AC2 Given 가공 완료 post조건이 아직 거짓 When 공정 진행 Then 완료 상태로 조용히 바뀌지 않는다.
- F4-AC3 Given 자재 무게가 Unit 능력보다 크거나 능력이 미정 When 비교 Then 각각 부족 또는 미정 Gap으로 근거를 표시한다.
- F4-AC4 Given 가정 크기와 초기 상태 When 저장·재열기 Then 가정 표기·단위·경로·초기 상태가 보존된다.
- F4-AC5 Given 참조 Unit 삭제 시도 When 영향 확인 Then 경로 단절을 알리고 사용자의 명시적 대체/해제 전 정상 흐름으로 처리하지 않는다. 삭제 방식은 제안이다.

### 8) 의존 / 미정

F3의 자재 능력, F5 전이, F6 비교, C04 실행과 연결된다. 자재 좌표 표현, 버퍼 큐 정책, 투입 간격 단위/기준, 크기 형상 표현과 첫 구현의 다중 자재 지원은 미정이다.

## 9. F5 Process Composer — SequenceDraft와 SFC

### 1) ID / 목적

[확정] F5-01 Action DnD, F5-02 자연어 Sequence Dictation, F5-03 공통 SequenceDraft → SFC, F5-04 모호함·전이·Interlock·Gap 검증. 설계자가 제공 능력을 공정 순서로 조합한다.

### 2) 상태 / 범위

[확정] 두 입력 방식은 동일 중간표현 SequenceDraft로 모이고 SFC(순차 기능 차트)로 이어진다. 자연어 해석의 모호함을 노출한다. 1·2등급 구조/Action 직접 지정은 결정적 변환, 3등급 의미 추론만 AI 사용이다. 필요 없는 AI 사용은 금지한다. [미정] 등급 경계의 세부 판별표와 자연어 문법은 아직 없다.

### 3) 입력 / 출력

입력은 Unit Action, 공정 요구, 자재 상태, 사용자 문장이다. 출력은 Draft 단계/Action 참조/전이조건/미정·모호함/Interlock 후보, SFC 표현, Gap 연결이다. [설계 제안] 원문 구절과 변환된 단계의 관계를 보관하고 시각 편집 수정 후 원문을 자동으로 사실처럼 재작성하지 않는다.

### 4) 정상 흐름

Action을 순서대로 놓거나 자연어 입력 → 입력 등급 판별 → 결정적 변환 또는 필요한 의미 추론 → Draft 확인 → 모호한 Action/대상/조건 선택 → 전이·Interlock 검사 → SFC 미리보기 → 저장 → 논리 실행 준비 검사.

### 5) 세부 규칙

- F5-05 [확정] 미정 전이조건과 Interlock 후보를 검증하고 Gap으로 연결한다. 추론이 애매하면 한 가지 결과를 몰래 확정하지 않는다.
- F5-06 [설계 제안] 단계 ID와 Action 인스턴스 매개변수를 분리한다. 동일 Action을 여러 단계에서 호출해도 정의를 복제하지 않고 참조한다. 완료 조건과 다음 단계 진입 조건의 차이를 표시한다.
- F5-07 [미정] 분기 우선순위, AND/OR 합류, 병렬 구간 완료·취소·오류 전파는 확정되지 않았다. [설계 제안] 첫 실행 규칙은 순차 경로부터 합의하고, 분기/병렬은 명시된 의미와 검수 자료가 있을 때만 실행 허용한다.
- F5-08 [확정] F7의 순서·병렬 변형은 제품 요구다. 단기 실행 제한은 병렬의 영구 제외가 아니다.

### 6) 예외

[설계 제안] 찾을 수 없는 Action, 같은 이름의 복수 후보, 타입이 맞지 않는 매개변수, 도달 불가 단계, 종료 없는 루프, 미정 조건을 각각 표시한다. AI 실패 시 문장을 보존하고 수동 Draft 편집으로 이어간다. AI 응답이 없는 Action을 생성했다면 확인 전 모델에 확정 추가하지 않는다.

### 7) 완료 검증

- F5-AC1 Given 동일 Action/순서를 직접 지정한 두 입력 When DnD와 구조화 문장으로 변환 Then 같은 의미의 Draft와 SFC를 얻고 AI를 호출하지 않는다.
- F5-AC2 Given ‘실린더를 이동’에 후보가 둘 When 해석 Then 선택 필요 상태를 표시하고 사람 선택 전 하나를 확정하지 않는다.
- F5-AC3 Given 미정 전이조건 When 실행 준비 검사 Then 관련 단계와 Gap을 표시하고 임의 true로 진행하지 않는다.
- F5-AC4 Given 사용자가 확인한 Draft When 저장·재열기 Then 단계 ID·Action 참조·조건·원문 출처·가정이 보존된다.
- F5-AC5 Given 실행 의미 미정인 병렬 구간 When 실행 요청 Then 현재 지원 경계를 알리고 정상 검증된 병렬 실행이라고 주장하지 않는다.

### 8) 의존 / 미정

F3 능력, F4 상태, C07 AI 경계, C04 실행, F8 SFC 매핑에 의존한다. Draft 스키마, 조건 언어, SFC 세부 표현, 자연어 등급 판별, 병렬·분기·루프 지원 단계는 미정이다.

## 10. F6 Gap Analysis — 요구와 제공의 차이

### 1) ID / 목적

[확정] F6-01 공정 요구 대 제공 능력 비교, F6-02 5종 Gap, F6-03 수정 위치 이동, F6-04 재분석과 해결 행 접기. 설계자는 누락과 제약을 근거와 함께 파악한다.

### 2) 상태 / 범위

[확정] Gap 종류는 부족 I/O, 부족 Unit, 미정 축 사양, 간섭 후보, 타이밍 병목이다. 항목은 근거·공정 단계·수정 제안을 가지며 Canvas/Configurator/Lab으로 이동한다. 수정 후 재분석하여 해결 행을 접는다. 간섭·안전은 사람 판단이고 자동 확정 종료하지 않는다.

### 3) 입력 / 출력

Process/Material 요구, Unit/Action 제공, Constraint, 시뮬/평가 결과를 입력받는다. 출력은 다섯 종류의 차이와 관련 객체·근거·수정 제안·상태다. [설계 제안] 하나의 Gap이 여러 공정 단계와 연결될 수 있고, 원인 누락과 파생 병목을 구별해 같은 문제를 과대 계수하지 않는다.

### 4) 정상 흐름

분석 대상/모델 리비전 선택 → 요구와 제공 수집 → 비교 → Gap 목록 확인 → 근거와 관련 단계 보기 → 편집 화면 이동 → 수정 → 재분석 → 해결된 일반 항목 접기, 안전/간섭은 확인 상태 별도 유지.

### 5) 세부 규칙

- F6-05 [확정] 가정은 Export에서도 유지한다. 논리 간섭 후보와 정밀 물리 검증을 분리한다. 간단 배치 중첩이나 자원 동시 사용 검사를 물리 안전 검증으로 부르지 않는다.
- F6-06 [설계 제안] 부족 I/O는 요구 역할과 제공 역할/방향·타입 대조, 부족 Unit은 필요한 능력 부재, 미정 축 사양은 실행/수용 판정에 필요한 사양 누락으로 설명한다. 후보 비교 알고리즘과 수치 기준은 승인 대상이다.
- F6-07 [설계 제안] 타이밍 병목은 해당 평가 가정·자재 수·투입 간격·시간 규칙을 함께 표시한다. 미정 시간이 있는 결과를 확정 택트로 표시하지 않는다.
- F6-08 [설계 제안] 해결 행 접기는 이력 삭제가 아니다. 확인을 숨김/보류/해결/사람확인필요와 구별하고 재등장 시 이전 근거와 연결한다.

### 6) 예외

[설계 제안] 비교할 정보가 부족하면 ‘문제 없음’이 아니라 비교 불가/미정으로 표시한다. 모델 변경 중 분석 결과가 도착하면 기준 리비전 차이를 알려 재분석을 요구한다. 이동 대상이 삭제되면 원인 ID와 마지막 근거를 남긴다. 안전 관련 수정 제안은 자동 실행하지 않는다.

### 7) 완료 검증

- F6-AC1 Given 요구 완료 Signal이 없음 When 분석 Then 부족 I/O와 해당 단계·역할·근거 및 Configurator 이동을 제공한다.
- F6-AC2 Given 축 사양이 미정 When 분석 Then 미정 축 사양으로 표시하고 정상 충족으로 판정하지 않는다.
- F6-AC3 Given 일반 부족 항목을 수정 When 재분석 Then 해결 행을 접되 이전 근거와 수정 연결은 유지한다.
- F6-AC4 Given 간섭 후보의 조건이 바뀜 When 재분석 Then 자동 안전 확정 종료하지 않고 사람 확인 상태를 보여 준다.
- F6-AC5 Given 가정 시간으로 계산한 병목 When 결과와 Export 확인 Then 가정과 평가 조건이 함께 보이며 정밀 물리 검증 완료로 표시되지 않는다.

### 8) 의존 / 미정

F3·F4·F5가 요구/제공 계약을 제공하고 C04·F7이 시간 결과를 제공한다. 각 Gap의 판정 규칙·심각도·중복 합치기·닫힘 정책·수치 임계값은 미정이다. 안전/간섭 자동 확정 금지 자체는 확정 요구다.

## 11. F7 Evolution Lab — 사람 통제하의 변형·평가

### 1) ID / 목적

[확정] F7-01 변형 공간/평가 기준 정의, F7-02 AI 대량 후보·세대 생성 평가, F7-03 Pareto/세대 최고점수/탈락·차이 표시, F7-04 명시적 선택·적용. Lab은 원본을 독단적으로 최적화하는 곳이 아니라 제안 공간이다.

### 2) 상태 / 범위

[확정] 사람이 버퍼 수, 축 속도, 배치, 순서, 병렬, Unit 대체, 투입 간격, 신규 Unit 허용 범위를 정의한다. 평가는 택트, 간섭 위반 제외, 비용 대리 지표인 I/O·Unit 수, 자재 대기를 다룬다. 기본은 경량 택트 평가이고 VC 물리는 선택 사항이다. 목업의 후보 수·초·가중치·최적화 효과는 [예시]이며 성능 보장이 아니다.

### 3) 입력 / 출력

기준 모델, 변형 허용 범위, 고정 조건, 평가 기준, 평가기 선택을 입력받는다. 출력은 후보 세대, 점수/지표, Pareto, 최고점수 추이, 탈락 사유, 원본과의 차이, 적용 후보다. [설계 제안] 평가 설정과 기준 리비전·가정·평가기 버전을 함께 보존한다. 가중합 점수와 원시 지표를 따로 표시한다.

### 4) 정상 흐름

기준 설계 선택 → 바꿀 수 있는 항목과 범위 지정 → 평가 기준/제약 지정 → 후보 생성/검증/평가 → 세대별 결과 확인 → Pareto/탈락/차이 비교 → 사람이 후보 선택 → 적용 영향 미리보기 → 명시 적용 → 원본 변경 이력 기록 및 재검사.

### 5) 세부 규칙

- F7-05 [확정] 사람 선택과 명시 적용 전에는 원본을 바꾸지 않는다. 신규 Unit도 허용 범위 안에서 제안한다. 간섭 위반 제외는 안전 인증이 아니라 설정된 평가의 제약 처리다.
- F7-06 [설계 제안] 구조적으로 잘못된 후보는 평가 전에 탈락시키고 이유를 남긴다. 미정 실행 의미를 가진 병렬 후보를 정상 택트로 평가하지 않는다.
- F7-07 [설계 제안] 경량 논리 결과와 VC 결과에 평가기 라벨을 붙여 비교한다. 하나의 그래프에 섞더라도 동일 정밀도인 것처럼 표시하지 않는다. 가정값 기반 후보는 그 가정을 드러낸다.
- F7-08 [설계 제안] 후보 적용은 한 편집 트랜잭션으로 하고 기준 리비전이 달라지면 재비교를 요구한다. 후보별 객체 ID 대응을 보관하여 차이 보기가 이름 비교에만 의존하지 않게 한다.

### 6) 예외

[설계 제안] 실행 취소·서비스 실패·평가 시간 초과·불가능한 범위·전 후보 탈락을 구별한다. 취소 시 완료된 결과를 유지할지는 미정이지만 원본은 바꾸지 않는다. 무한 작업이나 과금 위험을 막을 요청 상한·자원 예산·동시성은 구현 전 결정한다. VC 미연결 시 가능한 경량 경로와 불가한 물리 경로를 구별한다.

### 7) 완료 검증

- F7-AC1 Given 속도만 변경 허용 When 후보 생성 Then 고정한 배치·Unit 수는 바뀌지 않고 위반 후보는 탈락 사유가 표시된다.
- F7-AC2 Given 여러 후보와 상충 지표 When 결과 보기 Then Pareto·세대 최고점수·원시 지표·탈락 이유·차이를 확인할 수 있다.
- F7-AC3 Given 후보 평가 완료 When 아직 적용하지 않음 Then 원본 모델과 저장 내용은 기준 상태로 유지된다.
- F7-AC4 Given 사용자가 특정 후보 선택 When 영향 확인 후 명시 적용 Then 선택한 변경만 원본에 반영되고 이력 메모·재검사 대상이 남는다.
- F7-AC5 Given VC 실패 또는 작업 취소 When 결과 수신 Then 실패/취소를 성공 평가와 구별하고 원본을 보존한다.

### 8) 의존 / 미정

C07 어댑터·동의, C04 실행 규칙, F6 제약, F8 변경 이력과 연결된다. 세대 알고리즘·후보 수·초·가중치·비용 예산·재현성·난수 시드·최적화 효과 목표는 미정이다.

## 12. F8 Aurora Export/Round-trip — 매핑과 역매핑

### 1) ID / 목적

[확정] F8-01 매핑 준비 상태·미리보기·사람 확인, F8-02 Core 대상 Export, F8-03 실제 I/O·실측 Position 역매핑, F8-04 같은 모델과 가정의 연속성. 설계자가 초기 컨셉을 구현 설계로 넘기고 현장의 확정 정보를 되돌린다.

### 2) 상태 / 범위

[확정] Unit/Device 트리는 Core Configurator, Signal(DI/DO/AX)은 SignalMap, Position은 포지션 테이블, SequenceDraft는 SequenceDesigner SFC로 매핑한다. Interlock 후보는 override 가능한 기본값, Evolution 결과는 변경 이력 메모로 넘긴다. Material은 Core 자리가 없으면 MD에 보관한다. [미정] 실제 Core 스키마·버전·연동 범위. 목업의 3.0은 확정 버전이 아니다.

### 3) 입력 / 출력

입력은 확인된 모델, 가정/미정 목록, 매핑 규칙, 실제 I/O 주소표 및 실측값이다. 출력은 매핑 준비 상태, 변환 미리보기, 사람 확인 내역, 대상 계약에 맞는 산출물, 미매핑 보관 정보, 역매핑 결과다. [미정] MD 영역의 실제 보관 형식과 제품 용어는 후속 확인한다.

### 4) 정상 흐름

대상 버전/매핑 계약 선택 → 구조·신호·포지션·Draft·후보 점검 → 준비/미정/불가 상태 미리보기 → 가정과 누락 검토 → 사람 확인 → Export. 역방향은 실제 I/O 주소표 가져오기 → 이름/역할 자동 짝 후보 → 미일치 사람 연결 → 가정값을 실측으로 교체 → 관련 객체·공정 검사 → 동일 모델 저장으로 이어진다.

### 5) 세부 규칙

- F8-05 [확정] 자동 짝은 최종 사실이 아니며 미일치는 사람이 연결한다. 가정을 지우는 대신 실측으로 교체한 사실을 추적할 수 있어야 한다. 아직 남은 가정은 Export에서도 명시한다.
- F8-06 [설계 제안] 매핑 표는 원본 ID·대상 키·변환 규칙·단위·상태·근거를 담는다. 이름 충돌과 방향/타입 불일치는 매핑 준비 실패 또는 확인 대상으로 구별한다.
- F8-07 [설계 제안] Material 등 대상에 없는 의미는 원본 모델에 보존하고 Export 누락 목록을 낸다. 외부가 표현하지 못하는 값을 삭제해 호환된 것처럼 보이지 않는다.
- F8-08 [설계 제안] 역매핑은 주소만 바뀐 Signal의 내부 ID를 유지하고 변경 전후·출처·사람 확인을 기록한다. 단위 변환과 다대일 매칭은 별도 미리보기를 요구한다. 실제 제어기의 주소를 설정하거나 장비에 연결하지 않는다.

### 6) 예외

[설계 제안] 대상 스키마 불명, 변환 불가 조건, 중복 I/O 주소, 없는 대상 객체, 단위 불일치, 덮어쓰기 충돌을 표시한다. 확인 전 내보내기를 완료 처리하지 않는다. 부분 Export 허용 여부는 미정이며 허용하더라도 제외 목록·가정·원본 식별을 명시해야 한다. 외부 파일은 Undo로 회수되지 않을 수 있다.

### 7) 완료 검증

- F8-AC1 Given 모델과 확인된 대상 계약 When 미리보기 Then 각 트리/Signal/Position/Draft/Interlock/이력의 목적지와 가정·미매핑 상태가 보인다.
- F8-AC2 Given 실제 Core 버전·스키마 미확인 When Export 요청 Then 검증된 실제 연동이라고 표시하지 않고 계약 확인 필요를 알린다.
- F8-AC3 Given 주소표의 이름/역할 후보와 미일치 항목 When 역매핑 Then 미일치는 사람 연결 전 자동 확정되지 않는다.
- F8-AC4 Given 가정 Position을 실측으로 교체 When 저장·재열기 Then 원본 객체 ID·공정 연결을 유지하고 교체 출처 및 남은 가정을 볼 수 있다.
- F8-AC5 Given Core에 Material 필드가 없음 When Export Then 원본 영역에 Material이 유지되고 대상 제외 사실을 확인할 수 있다.

### 8) 의존 / 미정

F3·F5·F7 결과와 공통 확인/버전 계약이 필요하다. 실제 Core 스키마·버전·테스트용 교환 자료·Signal AX 의미·SFC 차이·override의 대상 의미·MD 보관 형식은 미정이다.

| D07 라이선스 | 리소스별 출처·사용/재배포 조건 기록 | 불명 자료는 패키지 자동 포함 보류. 사진 실패는 도식 대체 |

[설계 제안] 시뮬레이터의 한 가상 시각에서 ‘입력 상태 읽기 → 활성 Action 평가 → 완료/타임아웃 판단 → 전이 → 상태 기록’ 같은 평가 순서를 문서로 고정한다. 벽시계 속도와 논리 시간은 분리하되 시간 해상도·수치 오차 허용값·동률 정렬 규칙은 구현 전에 합의한다.

[예시] ‘가정 이동시간=단위 동반 수치, 확인상태=미확인, source=사용자 직접 입력, timeout=미정’인 Action은 값이 있다고 확정 사양이 되지 않는다. 이 예시는 JSON/AML 실제 스키마가 아니며 실행 가능한 코드가 아니다.

## 14. 첫 5공정 시나리오와 검수 데이터

[확정] 첫 테스트 장비는 아래 5공정이다. 문서상의 턴테이블·Tray 예제를 고정 장비 구조로 대체하지 않는다. 자재 한 개가 도착 → 정지 → 작업 → 완료 → 다음 이동 흐름을 따른다.

| 검수 단계 | 장치 구성 [확정] | 논리 완료 관찰점 [설계 제안] |
|---|---|---|
| S1 투입 | 푸셔 + 실린더 | 투입 Action 완료 후 식별 구간 이동 허용 |
| S2 식별 | 스토퍼 + 바코드리더 | 자재 정지 확인 후 읽기 완료, 결과/실패 상태 구별 |
| S3 가공 | 스토퍼 + 실린더, 가상 작업 | 정지 상태에서 가상 작업 완료 후 자재 가공상태 변경 |
| S4 이송 | 갠트리 + 피커 | 잡기·이동·놓기 완료와 자재 위치/소유 상태 연결 |
| S5 배출 | 스토퍼 + 컨베이어 | 배출 완료 시 종료 상태와 최종 자재 위치 표시 |

[설계 제안] 검수용 묶음에는 초기 Signal/Position/자재 상태, 모든 Action의 pre/post, 이동/작업 지연, 타임아웃, 기대 전이표를 포함한다. 수치는 실제 장비 사양이 아니라 [예시]로 표시하고 양 플랫폼에 같은 입력을 제공한다. 이동 경로와 동작 완료 Signal을 분리하여 한쪽만 연결된 오류도 검수한다.

SC-AC1 Given 한 자재와 완전한 조건 When 순차 실행 Then S1~S5의 기대 상태전이와 최종 배출 상태가 관찰된다. SC-AC2 Given S2 완료 신호 미발생 When 합의된 타임아웃 도달 Then 이후 공정으로 통과하지 않고 오류 근거를 기록한다. SC-AC3 Given S4 진행 중 When 일시정지·재개·초기화 Then 시간 동결과 초기 상태 복원을 각각 확인한다. SC-AC4 Given 사진/테마 변경 When 같은 입력 재실행 Then 논리 결과가 같다.

## 15. 양 플랫폼 동등성 검증 계획

[확정] 공통 파일·동작 규칙·데이터 의미가 같아야 한다. [설계 제안] 픽셀 단위 화면 일치가 아니라 아래 의미 결과를 비교한다. 테스트는 미수행이다.

| 검증 ID | 동일 입력·조작 | 비교할 결과 |
|---|---|---|
| X01 | 같은 에셋 하나 로드·배치·속성 수정·저장 | ID·정의참조·단위·포트·가정·출처의 의미 |
| X02 | 웹 저장→WPF 열기→저장→웹 열기 | 구조·연결·Action·Material·Draft 보존. 직렬화 순서는 비교 대상 아님 |
| X03 | 같은 초기 상태·전이표·가상 시간 설정으로 실행 | 단계 활성화/완료 순서, 전이 시각, Signal·Position·자재 상태, 최종 결과 |
| X04 | 지연 중 일시정지·같은 가상 시각에 재개·초기화 | 정지 중 시간 불변, 남은 지연, 초기 조건 복원 |
| X05 | 누락 참조·미지원 버전·타임아웃 입력 | 오류 종류·관련 객체·진행 차단과 원본 보존 |
| X06 | 도식/사진과 A/B/C 테마 전환 | 모델 의미·연결·실행 결과 불변, 없는 사진 대체 |
| X07 | 미확인 후보·Interlock·Lab 후보 적용 전 상태 | 사람 승인 전 반영 금지, 승인 후 지정 변경만 적용 |
| X08 | 가정 Position/Signal을 주소표·실측으로 역매핑 | ID·공정 연결 유지, 매칭 확인·변경 이력·남은 가정 보존 |

[설계 제안] 각 검수 결과는 입력 묶음 리비전, 앱/형식 버전, 실행 규칙 버전, 관찰 전이표, 차이, 확인자를 남긴다. 수치 허용 오차는 [미정]이며 편의상 임의 허용하지 않는다. WPF 결과는 사용자가 Windows에서 빌드·실행한 증거를 받아 기록한다. 웹 성공만으로 X02~X08의 WPF 통과를 선언하지 않는다.

## 16. 작은 수직 구현 순서 및 확장 계획 제안

모든 단계는 [설계 제안]이며 지금 구현을 시작하라는 승인이 아니다.

| 순서 | 작은 완료 단위 | 통과 조건 |

### 18.2 인계 체크리스트

- 이 문서가 계획이지 구현 결과가 아님을 확인한다. 현 시점 구현·테스트는 모두 미수행이다.
- 사용자 확정, 설계 제안, 미정, 예시를 그대로 분리한다. 목업의 3.0·성능 수치·화면을 실제 계약/측정으로 인용하지 않는다.
- Q01과 착수 필수 결정을 먼저 받고 승인된 작은 구현 묶음만 계획한다. F1~F8 전체 제품 요구를 삭제하거나 전체 동시 구현 승인으로 오해하지 않는다.
- 공통 계약과 검수 입력을 먼저 확정하고 웹 한 에셋의 끝단을 WPF와 조기에 왕복 검증한다.
- 실제 AML 공식 명세/XSD와 실제 Core 교환 계약을 확인하기 전 적합성·연동 성공을 주장하지 않는다.
- 회사 PC에 직접 접근하지 않는다. WPF 빌드/실행은 사용자가 수행하며 미수신 결과는 미검증으로 남긴다.
- 후보 반영, Interlock 확인, 안전·간섭 판단, Lab 적용, Export 확인의 사람 개입을 우회하지 않는다.
- 가정·출처·미정·Material·모델 ID를 변환 과정에서 보존하고 설계 데이터와 런타임 상태를 섞지 않는다.
- 저장소와 IssueReporter 분리, .NET, 브랜치, 보안·전송 동의를 확인한다. 이번 문서에 없는 값을 조용히 확정하지 않는다.
- 요구 변경 시 ID/상태/결정 이유/영향 AC를 기록하고 통과·실패·미구현·미검증을 구별한다.

### 18.3 현재 이양 완료 범위

이번 작성 산출물은 문서 파일 두 개다. 외부 저장/전달 상태는 별도 확인한다. 앱 소스·저장소 변경, 회사 PC 접근, 구현·빌드·실행·테스트는 미수행이다. AC·전이·연동 설명은 요구와 제안이지 성공 보고가 아니다.
